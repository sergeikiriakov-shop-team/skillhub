SkillHub

Общий реестр скиллов Claude Code, где сервер ничего не «думает» — думает Claude Code каждого разработчика.

Скиллы (SKILL.md) со всей команды собираются в одном месте: хранятся, ищутся векторным поиском, оцениваются по единой рубрике и ставятся к себе одной фразой. Вся «умная» работа выполняется на собственном аккаунте разработчика.

Python 3.12 · FastAPI React · Vite · Mantine Postgres 16 · pgvector MCP · OAuth 2.1 Один VPS · push-to-deploy Ревью: один поток · проверка 21.10

01 Зачем это нужно

Каждый пишет свои почти одинаковые скиллы. SkillHub собирает их в один каталог.

Сегодня разработчики независимо пишут дублирующие друг друга SKILL.md. SkillHub — это реестр, слой оценки качества и (в перспективе) синтеза «идеального» скилла из группы похожих.

Как было

  • Каждый держит свои скиллы локально, у всех разные версии.
  • Нет единого мнения, какой скилл лучше и когда его применять.
  • Дубли и пересечения никто не видит.
  • Оценка «на глаз» — у каждого свой критерий качества.

Как стало

  • Один каталог: одна запись на имя, история версий, подтверждённое авторство.
  • Единая рубрика качества → сопоставимые оценки для всех.
  • Векторный поиск и группировка по «работе» (task_group).
  • Установка скилла себе одной фразой в Claude Code.

02 Главный принцип

Работа идёт через собственный аккаунт каждого разработчика

Это ключевая архитектурная идея всего проекта. Сервис принципиально не вызывает LLM — ни ключа Anthropic, ни LangChain на сервере нет.

Как это работает

Сервер — это система хранения и раздачи: он держит скиллы и единую стратегию оценки и отдаёт их по GET /api/rubric. А оценку, категоризацию и синтез выполняет Claude Code каждого разработчика — на его собственном аккаунте. Claude Code тянет рубрику и очередь неоценённых скиллов, всё считает у себя и присылает результат обратно (POST /api/skills/{id}/assessment).

Поскольку сама стратегия хранится на сервере, все разработчики выполняют один и тот же алгоритм — оценки получаются сопоставимыми, а не «у каждого свой промпт».

💳 Свой аккаунт — свои вычисления

Нет общего API-ключа и центрального бюджета на токены. «Тяжёлую» работу оплачивает подписка Claude каждого разработчика. Нагрузка масштабируется вместе с командой.

🔑 Личность через GitHub

Разработчик входит под своим GitHub-аккаунтом (OAuth). Авторство скиллов и оценок привязано к проверенной личности — подделать нельзя.

📐 Единый алгоритм на сервере

Рубрика, правила категоризации, стратегия отбора и синтеза лежат в rubric.py и отдаются через API. Меняем стратегию в одном месте — обновляются все.

03 Архитектура и поток работы

Сервер в центре, Claude Code каждого разработчика — по краям

Ниже — как устроен обмен. Бирюзовым обозначено хранение и раздача (сервер), янтарным — вычисления (собственный Claude Code каждого разработчика).

db + mcp

Postgres 16 + pgvector для поиска. mcp — удалённый HTTP-сервер MCP за nginx (/mcp), точка входа для Claude Code.

MCP и API в деталях

Как удалённый MCP и REST API связаны через nginx и как проходит вход. SkillHub здесь — сам себе сервер авторизации (это api), а mcp — resource server: он проверяет присланный Bearer и форвардит тот же токен в API, который и применяет гейт чтения и роли.

OAuth-рукопожатие MCP

Стандартная авторизация MCP (spec 2025-06-18) — Claude Code проходит её сам, один раз.

  1. 1Claude Code → GET /mcp → 401 + WWW-Authenticate
  2. 2GET /.well-known/oauth-protected-resource/mcp (отдаёт mcp) → адрес AS
  3. 3GET /.well-known/oauth-authorization-server (отдаёт api) → метаданные AS
  4. 4Dynamic Client Registration → POST /api/oauth/register
  5. 5Authorization Code + PKCE → GET /api/oauth/authorize: браузер, вход через GitHub → code
  6. 6Token → POST /api/oauth/token (code + PKCE) → access + refresh
  7. 7GET /mcp с Bearer → mcp проверяет через /api/auth/me и форвардит токен в API

04 Жизненный цикл скилла

От загрузки до «идеального» скилла

Шаги без метки выполняет сервер; шаги с меткой Claude Code — собственный агент разработчика.

1

Импорт

parse → embed → persist. Версия создаётся только при смене хеша — реимпорт идемпотентен.

2

Оценка

Скоринг по рубрике v2: 6 измерений 0–10 + holistic overall.

3

Категоризация

Два уровня: широкая категория + узкий task_group («та же работа»).

4

Отбор

Внутри одного task_group выбирается лучший по overall.

5

Синтез

Из кластера собирается «идеальный» скилл по фиксированному алгоритму.

6

Рекомендации / Ревью

Куратор предлагает изменения; задачи проходят саморевью и отметку лида.

Дедупликация встроена в импорт: загрузка контента, идентичного существующему скиллу под другим именем, отклоняется (HTTP 409); просто похожий (косинус ≥ 0.90) — принимается с предупреждением. Так настоящие варианты живут под разными именами внутри одного task_group.

05 Аутентификация и роли

SkillHub — собственный сервер авторизации; GitHub даёт только личность

Одна таблица auth_tokens и один get_user_by_token обслуживают все входы. Провайдер намеренно изолирован (только /login + /callback), поэтому его легко заменить.

👤 Люди — браузер

Вход через GitHub (auth-code flow) → cookie skillhub_session. Кнопка в шапке портала.

🤖 Claude Code — MCP

Удалённый HTTP MCP по URL. Первый вызов инструмента открывает браузер для входа через MCP OAuth — ни Docker, ни токена вручную. Legacy stdio + device flow — запасной путь.

🚪 Гейт доступа

Войти может только тот, у кого есть доступ к настроенному GitHub-репозиторию. Админы гейт обходят. Чтения на прод-инстансе тоже закрыты (SKILLHUB_PUBLIC_READS=false).

Роли — по возрастанию прав

viewerсмотрит каталог → contributorзагружает скиллы → evaluatorотправляет оценки → adminуправляет пользователями

Любой GitHub-аккаунт начинает как viewer. E-mail из SKILLHUB_BOOTSTRAP_ADMINS становится admin при первом входе; дальше админ повышает остальных. Роли — это понятие самого SkillHub, провайдер их не несёт.

Лид — не отдельная ступень, а флаг is_reviewer поверх любой роли. Только с ним (или с ролью admin) доступны Approved и возврат задачи на доске ревью.

Кто это настраивает. Админ меняет роли и флаг лида на странице /users (ссылка в меню аккаунта, видна только админам) или фразой в Claude Code через MCP-инструменты set_user_role и set_reviewer. Свою собственную роль админ поменять не может: сервер отвечает 409, это делает другой админ.

06 Рубрика оценки · v2

Единая мера качества — одна для всех рецензентов

6 измерений по 0–10. overall считает сервер как взвешенное среднее; веса хранятся в БД и меняются админом, после чего весь каталог пересчитывается сразу. Версия рубрики хранится в каждой оценке: при смене рубрики старые оценки помечаются как устаревшие, а не переписываются молча.

Измерения и живые веса

safety — предупреждения о разрушительных действиях и крайних случаях×3
completeness — покрыт ли рабочий процесс без пробелов×2
reusability — переиспользуемость, а не разовость×2
trigger_quality — насколько точно указано, КОГДА срабатывать×1.5
clarity — ясность и однозначность×1
structure — заголовки, примеры, references×1

Значения из GET /api/rubric на 21.10. Стартовые веса в rubric.py другие (trigger и completeness ×2, остальные ×1); действуют те, что в БД.

Калибровочные якоря

Одинаковый смысл балла у всех — оценки сопоставимы.

9–10ExemplaryЛучшее в классе: точный триггер, полный процесс, явные предохранители.
7–8StrongГотов к использованию с мелкими пробелами.
5–6ServiceableРаботает, но заметно неполон или слишком общий.
3–4WeakРазмытый триггер, пропущены шаги или нет предупреждений.
0–2PoorПо сути не рабочий скилл или заглушка.

Двухуровневая таксономия

Широкая категория (primary_category) — куда скилл относится в общем. Узкий task_group — конкретная «работа» скилла (например sql-data-read, react-authoring). Скиллы, делающие одну и ту же работу, обязаны иметь общий task_group — именно это позволяет конкурирующим вариантам от разных разработчиков сходиться в один кластер, отбираться и синтезироваться в «идеальный».

09 Блок ревью

Один поток: разработчик проверяет свой дифф, доска показывает статус, лид подписывает

Ревью выполняет Claude Code автора на его собственном изменении. Каким скиллом проверять, решает сервер, поэтому все проверяются одинаково и результаты сопоставимы. Прогон сам ставит задачу на доску. Лид ничего не перезапускает: он читает находки и ставит Approved или возвращает задачу с причиной.

Разработчик

Саморевью

скиллы self-review · review-status

  1. Читает политику: какая дорожка (backend, frontend, default) и какой каталожный скилл её проверяет.
  2. Берёт этот скилл из каталога и применяет к своему диффу origin/master8...HEAD.
  3. Отправляет находки с severity, коммитами и адресом репозитория, поэтому каждая находка ведёт на свою строку в GitHub.
  4. После правок отмечает, какой коммит что закрыл, и запускает прогон заново.
get_self_review_policy · get_skill · submit_self_review · record_self_review_fixes · list_review_board(mine)
SkillHub

Доска задач

одна строка task_reviews на задачу

  1. Первый прогон создаёт строку задачи, следующие её обновляют.
  2. Вердикт считает сервер: любой blocker или major даёт changes_needed, иначе pass.
  3. Статус задачи берётся из последнего прогона, вручную его никто не выставляет.
  4. Находки не переписываются. Фиксы добавляются рядом: с коммитом это закрытие, с одной заметкой это ответ.
/api/self-reviews · /api/task-reviews · страница /reviews на портале
Лид

Подпись

скилл review-board, обычно под /loop

  1. Берёт очередь: задачи со статусом passed.
  2. Читает последний прогон целиком: находки, фиксы, прошлые прогоны.
  3. Ставит Approved или возвращает задачу с обязательным комментарием.
  4. Если дорожка помечена required, одобрить задачу без чистого прогона нельзя: сервер ответит 409.
list_review_board(passed) · get_task_review · approve_task_review · return_task_review

Как меняется статус задачи на доске

Удалить прогон или строку задачи может автор, пока задача не одобрена, и админ в любой момент. После удаления прогона статус задачи пересчитывается по оставшимся.

Итог

Технически всё на месте: каталог раздаёт актуальный скилл-ревьюер, скиллы потока лежат в каталоге и оценены, админ управляет ролями и флагом лида из портала или из Claude Code. Блокеры запуска

  • блокер

    Лид не назначен

    Флаг is_reviewer по-прежнему не стоит ни у кого. Админов теперь двое живых, но ревьюерами они быть не собираются, а review-board рассчитан на лида.

    Что сделать: выбрать лида; он один раз входит на портал через GitHub, админ включает «Лид на доске» на странице /users или говорит Claude Code «сделай <имя> лидом».

  • блокер

    Скиллы потока не установлены

    Все три в каталоге: self-review (id 50), review-status (id 52), review-board (id 51). В Claude Code у людей их пока нет.

    Что сделать: разработчикам — «установи скиллы self-review и review-status из SkillHub», лиду — «установи review-board из SkillHub».

Риски

  • риск

    Можно одобрить непроверенный код

    Нашла независимая оценка. Ни review-board, ни review-status не сверяют вершину ветки с коммитами чистого прогона. Если автор допушил после прогона, лид увидит зелёную задачу и одобрит то, что скилл не видел.

12 Как начать

Подключение за одну команду

MCP работает на сервере — ни Docker, ни образа, ни токена не нужно.

claude mcp add --transport http --scope user skillhub https://166.1.29.218.sslip.io/mcp # при первом вызове инструмента Claude Code сам откроет браузер для входа через GitHub

Если установлен скилл connect-skillhub, можно просто сказать Claude Code: «установи SkillHub MCP для https://166.1.29.218.sslip.io». После подключения — обычным текстом:

что есть в SkillHub про SQL?
импортируй этот SKILL.md в SkillHub
оцени неоценённые скиллы в SkillHub
установи скилл <имя> из SkillHub в мой проект
сделай саморевью моей задачи перед сдачей
/loop 15m review-status — разработчик ждёт решения лида
/loop 15m review-board — лид разбирает очередь
